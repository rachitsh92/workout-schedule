CONTRACT
Request: { "tenant_id": string, "flow_id": string, "otp": string }
- Malformed JSON or missing/empty tenant_id, flow_id or otp -> 400 generic.
- otp is expected to be 4-8 digits. A non-numeric or wrong-length otp must NOT be revealed as a format error: treat it like a wrong code (RecordFailure, 401) without calling VerifyOtp.
Success 200: { "reset_token": "<opaque>", "expires_in": <policy.ResetTokenTTLSeconds> }
Errors (exactly these):
  401 { "error_message": "Invalid or expired code" }  -> EVERY verification failure, identical body and headers
  429 { "error_message": "Too many attempts. Please restart recovery." } -> locked out
  503 -> Redis/cache error or notification sender transport error
Never reveal "decoy", "expired" or "disabled" to the client.

FLOW (execute in this order)
1. Resolve tenant config and policy := GetRecoveryPolicy(). Unknown tenant or recovery disabled -> 401 (generic; see Open Question 1).
2. recoveryCache.Get(flow_id):
   - cache.ErrNotFound -> 401
   - cache.ErrStoreUnavailable -> 503
   - ANY other error -> 503 (never fall through with a nil flow)
   - flow.TenantID != request tenant_id -> 401
3. Lockout check BEFORE looking at the OTP: lockoutKey := "recovery:" + flow.IdentifierHash (identifier hash, NEVER the flow id, so restarting a flow does not reset the attempts). lockoutService.IsLocked(ctx, tenant, lockoutKey, tenantCfg, constants.OTP_LOGIN_FACTOR).
   - Locked -> recoveryCache.Delete(flow_id) -> 429.
   - IsLocked returns an error -> 503. Fail closed.
4. Decoy or empty OTPRefID (flow.Decoy == true || flow.OTPRefID == ""):
   - lockoutService.RecordFailure(...) with the same key and factor.
   - If the account is now locked: Delete the flow -> 429 (same progression as a real flow). Otherwise 401.
   - Do not call VerifyOtp. Decoys must consume attempts and follow the same lockout progression as real flows.
5. Re-check the identity: GetIdentity(flow.TenantID, flow.IdentityID).
   - If it is not active, or isExternalIDP(traits): Delete the flow -> 401. Log INFO category "disabled_mid_flow".
   - GetIdentity returns an error: log ERROR "recovery_lookup_failed", do NOT record a failure -> 503.
6. Malformed otp (not 4-8 digits): treat as a wrong OTP (RecordFailure + the same locked check as step 7), skip VerifyOtp.
7. sender, err := notificationSenders.GetSender(tenant); err -> 503 (no RecordFailure).
   err := sender.VerifyOtp(ctx, flow.OTPRefID, otp):
   - err is sender_util.ErrCodeOtpVerificationFailed (match as the repo does) -> RecordFailure; if now locked: Delete the flow -> 429; else 401.
   - any other error (timeout, network) -> 503. Do NOT call RecordFailure for system errors.
   - nil -> correct OTP.
8. Success path (this order):
   a. lockoutService.ClearAttempts(...) (same key and factor). A failure here: log ERROR, don't fail the request.
   b. recoveryCache.Delete(flow_id) (single-use). Error -> 503.
   c. token, err := recoveryCache.CreateResetToken(ctx, flow.TenantID, flow.IdentityID, policy.ResetTokenTTLSeconds * time.Second). ErrStoreUnavailable (or any error) -> 503.
   d. Return 200 { reset_token, expires_in: policy.ResetTokenTTLSeconds }.

SECURITY RULES
- Every 401 path has an identical body, status and headers. Locked is the only different (429) response.
- Decoy and real flows produce the same status codes and the same lockout progression.
- Apply the same response-time floor/jitter helper used by initiate on every 401 and 429 path, so a decoy (no VerifyOtp call) cannot be told apart from a real wrong-OTP by latency. Add a TODO to measure and tune.
- NEVER log: the OTP, flow_id, reset token, identifier, identityID, OTPRefID, recipients, or raw error text (%v of an error). Log only tenant, outcome category, error class and a short fingerprint (first 12 hex chars of sha256(flow_id)).
- Audit (A4 allow-list covers /v2/recovery/): tenant, fingerprint, outcome category. Use distinct categories: validate_success, invalid_code, decoy_invalid_code, flow_not_found, tenant_mismatch, locked, locked_on_failure, disabled_mid_flow, sender_error, store_unavailable. Write an audit entry on the 503 paths too.
- Use ctx.Request.Context() consistently when calling services.
- The reset token comes only from CreateResetToken (crypto/rand). Do not generate anything here.
